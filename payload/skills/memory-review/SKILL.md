# /memory-review — メモリの棚卸しと昇格

**前提として読むもの:** `~/.claude/rules/self-improve.md` の「横断昇格の基準」。
どこへ昇格させるかの判断はそこが正本。

## 引数

| 呼び方 | 範囲 |
|---|---|
| `/memory-review` | **今のプロジェクトだけ**を整理する |
| `/memory-review all` | **全プロジェクトを横断**して棚卸しし、昇格候補を出す |

---

## A. `/memory-review`（プロジェクト内）

**`anthropic-skills:consolidate-memory` スキルを呼び、それに従う。**
重複マージ・陳腐化の除去・インデックス整理はそちらが実装している。再実装しない。

そのうえで、この環境固有の追加規約を守ること:

- **日本語で書く。**既存メモリの本文は日本語。英語で書き直さない
- **`[[name]]` リンクを壊さない。**リンク先は memory だけでなく
  `~/.claude/rules/*.md` や `~/.claude/skills/*/` も指す
- **INBOX と重複させない。**`~/.claude/learnings/<proj>/INBOX.md` に未処理が
  残っていれば、そちらを先に処理する（`self-improve.md` の手順）
- 終わったら `~/.claude/learnings/memory-review-state.json` の
  `last_review` を今日の日付に更新する

---

## B. `/memory-review all`（横断）

### 手順1 — 素材を集める

```
python C:\Users\yanagawa\.claude\hooks\memory_scan.py --json
```

LLM を使わない走査スクリプト。完全重複・近いペア・インデックスの不整合・
肥大・経過日数を出す。**判断はしていない。素材でしかない。**

出力が大きいので、必要なら `--project <スラッグ>` で絞る。

> **出力を別プロセスにパイプで渡すときは、必ずバイト列で読んで UTF-8 で
> 明示デコードすること。**この PC の Python は stdin を cp932 で読むため、
> テキストモードのままだと JSON が壊れる（2026-08-25 実測。同じ入力で
> cp932 読みだけが `Expecting ',' delimiter` で失敗する）。
>
> 出す側は対策済みなので、`PYTHONIOENCODING` を付ける必要はない。

### 手順2 — 自動で直してよいもの

**インデックスの不整合だけ**を、確認を取らずに直す。
ポインタと実ファイルの食い違いには判断の余地がないため。

| `kind` | 直し方 |
|---|---|
| `broken_link` | `MEMORY.md` からその行を削除する |
| `orphan` | `MEMORY.md` に1行足す。hook は `description` を縮めて使う |
| `dangling_wikilink` | **直さない。**報告だけする（書くべきメモリの予告かもしれない） |

### 手順3 — 判定して提案する

残りは**すべて提案に留め、user の承認を得てから適用する。**

| 判定 | 意味 |
|---|---|
| `RETIRE` | 完了済み・期限切れ。残す価値のある結論だけ別ファイルへ畳んで、元は消す |
| `MERGE` | 重複。内容の厚いほうのパスを残し、薄いほうを畳む |
| `PROMOTE→rules` | 複数プロジェクトで成立する**制約・好み**。短く書ける |
| `PROMOTE→skill` | 複数プロジェクトで使う**手順・技法**。長い |
| `SPLIT` | 1ファイルに複数の事実が入っている。分ける |
| `KEEP` | 据え置き |

判定は必ず**理由つき**で出す。理由には `memory_scan.py` が出した根拠
（共有している希少語、バイト数、経過日数）を引くこと。

**提案は表で出す。**対象 / 判定 / 理由 / 影響（どのファイルがどうなるか）。

### 手順4 — 適用する

承認された項目だけ適用する。終わったら
`~/.claude/learnings/memory-review-state.json` を更新する。

```json
{
  "last_review": "YYYY-MM-DD",
  "scope": "対象にしたプロジェクト",
  "counts": { "<プロジェクトスラッグ>": 棚卸し後の件数 }
}
```

**`counts` は必ず書く。**次回の通知は「絶対の件数」ではなく
**この値からの増加**で判定する。書かないと、そのプロジェクトは
「未棚卸し」とみなされて毎回通知が出る。棚卸ししなかったプロジェクトは
`counts` に含めないこと（未棚卸しとして正しく通知される）。

## 守ること

**完全重複ファイルを自動で削除しない。**memory はプロジェクト単位で隔離されて
おり、そのプロジェクトのセッションでしか読み込まれない。片方を消すと、
そのプロジェクトから知識が消える。**昇格候補として提示するに留める。**

**昇格しても元のメモリを消さない。**1〜2行に縮めて昇格先を `[[name]]` で指す。
プロジェクト固有の「いつ・どう当たったか」は昇格先には書けないため。
前例は `~/.claude/rules/svn-default-repo.md` が `[[project_svn_repo]]` を
参照している形。

**`rules/` に手順を書かない。**`rules/` は毎セッション全文が読み込まれる。
判断の前提になるものだけを置き、手順は必ず skill に置く。
**目安の上限は 15,000B**。超えるなら、新規追加より先に既存の圧縮を行う。
現在値は実測すること:

```
wc -c ~/.claude/CLAUDE.md ~/.claude/rules/*.md
```

（2026-08-25 時点で 14,955B。**余裕は 45B しかない。**次に足すなら、
まず既存を削るところから始める。）

**横断レビューは他プロジェクトの文脈を持たない。**`RETIRE` と `MERGE` の
誤りは知識の消失に直結する。迷ったら `KEEP` にして user に聞く。
