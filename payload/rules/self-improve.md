# 自己改善プロトコル — INBOX からの学習昇格

セッション終了ごとに、フック (`~/.claude/hooks/session_end_learn.py`) が
Haiku でそのセッションの知見候補を抽出し、`~/.claude/learnings/<proj>/` の
`INBOX.md` に積む。本書は、その INBOX をどう扱うかの規約。

上位のシステム指示・法令・安全ポリシーはこの規約より優先する。[[fable-partner]]
（対等なパートナーとしての姿勢）とは独立の関心事: あちらは対人態度、
本書は「自動生成された未検証の知見をどう扱うか」を定める。

## 位置づけ

INBOX の中身は Haiku が会話ログだけを見て機械的に抽出したものであり、
**未検証**。[[fable-kata]] の「9. 確かめたことだけを言う」の対象にはならない
（そもそも Claude 自身が確かめた事実ではない）。だからこそ INBOX から直接
`memory/` に転記してはならない。必ず精査を挟む。

## セッション開始時の動作

`~/.claude/hooks/session_start_inbox.py` が、そのプロジェクトの INBOX.md に
未処理項目があれば件数とファイルパスを標準出力に出す（LLM は使わない、
単なる件数通知）。作業を始める前に、この通知が出ていれば軽く目を通す。

## 昇格するかどうかの判断基準

INBOX の各項目について:

**昇格する（`memory/` に frontmatter 付きファイルを作り、MEMORY.md に
1行ポインタを足す）**:
- 次回以降のセッションでも成立する一般的な事実・好み・環境の制約
- 実際にこのセッション中に user から得た訂正・確認済みの方針
- 既存の `[[name]]` メモリと矛盾せず、かつ重複しないもの

**昇格しない（INBOX に残さず削除してよい）**:
- そのセッション限りの一時的な文脈（例: 「今日はこのファイルを直した」）
- リポジトリのコードや git 履歴を読めば分かること
- Haiku の誤読・過度な一般化に見えるもの
- 既存メモリと矛盾するが、どちらが正しいか確認していないもの
  （この場合は昇格せず、user に確認してから判断する）

## 手順

1. INBOX.md の該当エントリから詳細ファイル（同じディレクトリの
   `YYYY-MM-DD-<sid8>.md`）を読む
2. 上記基準で判断する
3. 昇格するものは既存の memory/ の作法（1事実1ファイル、frontmatter、
   `MEMORY.md` への1行追記、関連メモリへの `[[name]]` リンク）に従って書く
4. 判断が済んだ行（昇格した・しないを問わず）は INBOX.md から削除する。
   詳細ファイル自体は消さなくてよい（監査用に残る）

## 横断昇格の基準 — memory から rules / skill へ

memory はプロジェクトごとに隔離され、そのプロジェクトのセッションでしか
読み込まれない。**昇格しない限り、何件貯めても他プロジェクトでは1件も効かない。**

`/memory-review all` で棚卸しするとき、昇格先は次で決める。

| 条件 | 行き先 | 根拠 |
|---|---|---|
| 2プロジェクト以上で成立する**環境の制約・user の好み**で、短く書ける | `~/.claude/rules/<topic>.md` | 毎セッション全文が読まれる。判断の前提になるものだけ |
| 2プロジェクト以上で使う**手順・技法**で、長い | `~/.claude/skills/<name>/SKILL.md` | 必要なときだけ読まれる。長くてよい |
| 1プロジェクト限定 | `memory/` に据え置き | |

**`rules/` に手順を書かない。**毎回の文脈を食うため。手順は必ず skill へ。
`rules/` の合計は**目安として 15,000B を上限**とし、超えるなら新規追加より先に
既存の圧縮を行う。

**昇格しても元のメモリを消さない。**1〜2行に縮めて昇格先を `[[name]]` で指す。
プロジェクト固有の「いつ・どう当たったか」は昇格先には書けない。
前例は [[svn-default-repo]] が [[project_svn_repo]] を参照している形。

**完全重複ファイルを自動削除しない。**片方を消すと、そのプロジェクトから
知識が消える。昇格候補として提示するに留める。

## メモリの棚卸し

すでに memory/ に入ったものも定期的に見直す。溜まる一方では重複も陳腐化も落ちない。
`/memory-review`（今のプロジェクト）と `/memory-review all`（横断）で行う。
セッション開始時の通知が目安。手順はスキル側にある。

## 手動実行

SessionEnd フックが発火しなかった場合（アプリの強制終了など）の保険として
`/learn` コマンドがある。今の会話から知見を抽出し、上記と同じ判断を
その場で行う。
