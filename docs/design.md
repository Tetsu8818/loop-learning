# 設計メモ — 元記事との差分

元記事: https://zenn.dev/miyan/articles/claude-code-self-improving-system
（2026-08-20 時点の内容を WebFetch で取得して要約したものを基にした）

この文書は「記事のとおりに作らなかった箇所」と、その理由を実測ベースで
記録する。記事自体を否定するものではなく、この PC の実環境（Windows /
CLI 未導入 / 既存の Auto Memory 運用あり）に合わせた適応の記録。

## 1. Stop フック → SessionEnd フック

記事は Stop フックを「セッション終了時」の処理として使っている。

**実測（公式ドキュメント `code.claude.com/docs/en/hooks`）:** `Stop` は
「Claude finishes responding」、つまり **1ターンの応答が終わるたびに**
発火する。マルチターンの会話では1セッションで数十回発火しうる。

記事のスクリプトは Stop 発火のたびに `claude -p --model haiku` を呼ぶ。
そのまま採用すると、1セッションでの API 呼び出し回数が「セッション数」
ではなく「ターン数」に比例し、コストとレイテンシが記事の想定より
一桁以上増える。

→ 本実装は `SessionEnd` を使う。これはセッションが終了するときに一度だけ
発火する（`SessionEnd` イベントの `reason` フィールドで `clear` /
`resume` / `logout` / `prompt_input_exit` / `other` を区別できる）。

## 2. 抽出結果の書き込み先: MEMORY.md 直接追記 → INBOX 経由の二段階

記事: `>> "$MEMORY_DIR/MEMORY.md"` で Haiku の出力をそのまま追記する。

**実測:** この PC の既存 `MEMORY.md`（例: bihinyoyaku, ankenkanri など
8プロジェクト分を確認）は、1行1件の Markdown リンク形式のインデックス
であり、本文は `frontmatter` 付きの個別ファイルに分けて置く運用が
すでに定着している（`~/.claude/CLAUDE.md` の「メモリ」節に規定あり）。

Haiku の生出力（箇条書き3行程度、frontmatter なし）をそのまま
`MEMORY.md` に追記すると、この構造と混在し、インデックスとしての
一覧性が壊れる。またフォーマット規約（`type: user|feedback|project|
reference` 等）を満たさないファイルが増える。

→ 本実装は Haiku の出力を `~/.claude/learnings/<proj>/INBOX.md` という
**別の場所**に積む。`memory/` への昇格（正規フォーマットでの保存）は、
次回セッションで Claude 本体が INBOX を読んで判断する
（`~/.claude/rules/self-improve.md` に基準を明文化）。

## 3. bash + jq → Python 3.12

記事のスクリプトは bash + jq 前提。

**実測:** `jq` は未インストール（`which jq` で確認）。Python 3.12.10 は
インストール済み。Windows のシェル引用符・パス区切りの問題を避けるため、
フック本体は Python で書き、`settings.json` 側は `command` + `args`
配列（exec 形式）で呼ぶ。shell 経由のクォート展開を経由しないので、
パス中の空白やバックスラッシュで壊れない。

## 4. `claude -p` の呼び出し方: 引数直渡し → stdin 経由

記事はプロンプトをコマンドライン引数として渡す例になっている
（長いプロンプトを想定していない）。

**実測（`claude --help`）:** `-p, --print` は「prompt」を位置引数として
受け取れるが、標準入力からも読める。トランスクリプトのダイジェストは
最大 40,000 文字になりうり、Windows のコマンドライン長制限
（`CreateProcess` で概ね 32,767 文字）に抵触するおそれがある。

→ 本実装は `subprocess.run(..., input=prompt, ...)` で **stdin 経由**に
統一した。

## 5. 再帰防止: 環境変数ガードのみ → `--safe-mode` + 環境変数ガードの二重化

記事には子プロセスでのフック再帰に関する記述がない。

**実測（`claude --help`）:** `--safe-mode` フラグは「CLAUDE.md, skills,
plugins, hooks, MCP servers, custom commands and agents, output styles,
workflows, custom themes, keybindings」を含む全カスタマイズを無効化する
公式フラグで、`CLAUDE_CODE_SAFE_MODE=1` が設定される。フックから呼ぶ
子プロセスの `claude` にこれを付ければ、子プロセスでフックが評価されず
再帰が起きない。これを一次防御とし、`CLAUDE_SELFIMPROVE_CHILD=1` の
環境変数ガード（`os.environ.get(...) == "1"` で即 exit）を二次防御として
併用した。理由: `--safe-mode` は仕様変更・バグで無効化される可能性が
ゼロではないため、独立した二つの機構で守る。

さらに `--no-session-persistence`（呼び出しをディスクに残さない）と
`--max-budget-usd`（1回あたりの上限、暴走時の歯止め）を付けた。

## 6. コスト上限

記事にコスト上限の指定はない。本実装は CLI 呼び出しごとに
`--max-budget-usd 0.15` を付けている（`lib_transcript.DEFAULT_MAX_BUDGET_USD`）。
当初は 0.10 だったが、実費の揺れで断続的に失敗するため引き上げた（§13）。

**この節は 2026-08-24 に全面的に書き直した。それ以前の記述（上限 0.05、
1回あたり $0.01 未満）は、実測に基づかない見積もりで、実際とは4〜10倍
ずれていた。**コードの既定値は最初から 0.10 で、ドキュメントの 0.05 とも
食い違っていた。

実測（`--output-format json` の `total_cost_usd`、Haiku 4.5）:

| digest の長さ | 実費 |
|---|---|
| 9,000文字 | $0.0406 |
| 18,000文字 | $0.0585 |
| 20,000文字 | 約 $0.062（外挿） |
| 40,000文字 | 約 $0.102（外挿） |

1文字あたり約 $0.000002、固定費が約 $0.023。固定費が大きいのは、
`--safe-mode` でもシステム側の入力が2万トークン程度あるため。digest を
短くしても、1回あたり $0.04 は下回らない。

この実測から2つの帰結がある。

1. **`MAX_DIGEST_CHARS` を 40,000 から 20,000 に下げた。**40,000文字だと
   推定 $0.102 で上限 $0.10 を必ず超え、抽出が確実に失敗していた
   （§12 参照）。20,000文字なら約 $0.062 で、上限に対して1.6倍の余裕がある。
   実際に成功していた抽出の digest は約18,000文字だったので、内容量としても足りる。
2. **1回 $0.04〜$0.07 かかる。**「ほぼタダ」ではない。1日に数回動けば
   月に数ドルの規模になるので、抽出の当たり外れは費用対効果の問題として
   評価する必要がある。

## 7. `everything-claude-code` (ECC) は導入しない

記事後半で紹介されている `/instinct-status` 等のコマンド群は、

**worker はプロセスとして切り離す。**async フックのまま Haiku を呼ぶと、
セッションが短い場合に親の終了で道連れになる（実測: `--print` の1往復
セッションで対象選定まで進んだあと完走せずに殺された）。フック本体は対象を
選んで `DETACHED_PROCESS` で worker を起動するだけにし、即座に終わる。
実測では親 CLI の終了から25秒後に worker が完走した。

## 9. 抽出プロンプトの構造（2026-08-24 追加）

指示を先頭に置き、末尾に会話ログを置く形だと、**Haiku がログの続きを

1 だけでは「たまたま今回は効いた」の域を出ないため、2 を併用している。

## 11. コンソール窓の抑止と worker の直列化（2026-08-24 追加）

**症状:** 作業中、黒いコンソール窓（`claude`）が定期的に前面に現れる。

**原因（実測）:** `spawn_worker()` は worker を `DETACHED_PROCESS` で起動するため、
worker はコンソールを持たない。その worker の中で `call_claude_cli()` が
`creationflags` を指定せずに `claude.exe`（コンソールアプリ）を起動するので、
Windows が新しいコンソールを割り当てる。これが画面に出る窓の正体。

対照実験（同一条件で `claude.exe --version` を起動）:

| 条件 | 新規に生まれたコンソールホスト |
|---|---|
| `creationflags` なし（修正前） | 2個 |
| `CREATE_NO_WINDOW` あり（修正後） | 0個 |

→ `call_claude_cli()` の `subprocess.run` に
`creationflags=subprocess.CREATE_NO_WINDOW` を渡す。`getattr` 経由で取得して
いるので、非 Windows でも壊れない。

**併せて worker を直列化した。** 実測では 13:57:26 / :29 / :29 と3秒間に3本、
続けて 13:58 に2本の worker が同時に起動していた。各 worker は `claude.exe` を
呼び、`claude.exe` は起動のたびに `~/.claude.json`（27プロジェクト分の状態を
持つグローバルなファイル）を書き換える。デスクトップアプリも同じファイルを
書くので、多重に走らせる利点がない。同日には worker が2本、異常終了もしている
（`exit 129` / `exit 1`、原因未調査）。

→ `lib_extract.acquire_lock()` / `release_lock()` を追加し、
`session_start_catchup.py` と `session_end_learn.py` の両方から取得する。
ロックはプロジェクト別ではなく全体で1つ（競合する資源がグローバルなため）。
取り残されたロックは 900 秒で奪える。ロックの保持者は、catchup では worker
（`run_worker` の `finally`）、SessionEnd ではフック本体。

**未確認:** この時期にデスクトップアプリの会話が1本消えたが、因果は特定して
いない。消失時点で `~/.claude.json`（53KB / 27プロジェクト）もトランスクリプト
8本もすべて無傷だったため、この worker が破壊した形跡はない。ただし
「グローバルなファイルを複数プロセスで同時に書く」構造自体は危険なので、
因果の有無によらず直列化した。

## 12. `exit 1` / `exit 129` の正体は予算超過だった（2026-08-24 追加）

**症状:** 抽出がときどき失敗し、ログには `CLI call failed: exit 1: ` と
理由なしで残る。8/21・8/22 の `pre_compact_snapshot` の3件、8/24 の
`catchup` の2件が該当。

**なぜ理由が見えなかったか:** `call_claude_cli()` は失敗時に `stderr` だけを
ログに載せていた。しかし CLI は予算超過を **stdout** に出す。

```
returncode = 1
stderr     = ''          ← ログにはこれだけが載っていた
stdout     = 'Error: Exceeded USD budget (0.1)'
```

→ 失敗時は stderr と stdout の両方を見るようにし、予算超過は専用の
メッセージでログに残す。**この1点のせいで、原因の分かる不具合が4日間
「原因不明」になっていた。**失敗を記録するときは、握っている情報を全部
出すこと。

**なぜ超えたか:** §6 の実測のとおり、digest 40,000文字では推定 $0.102 で
上限 $0.10 を必ず超える。`pre_compact_snapshot` は「コンテキスト圧縮の直前」
＝会話が最も長い時点で動くので、digest が上限に張り付き、**構造的にほぼ必ず
失敗する**状態だった。3件の失敗はすべてこれで説明がつく。

**コストの主因は入力ではなく出力だった。**同じ 20,000文字の digest でも、
セッションによって実費が大きく変わる。

| 対象 | 出力トークン | 最終的な本文 | 実費 |
|---|---|---|---|
| `6d20e2ae` | 約1,300〜2,100 | 3行 | $0.04〜0.06 |
| `1c39edfa` | **7,530** | **88文字** | **$0.0943** |

`num_turns` は 1 で、ツールは使っていない（当初「ツールを使って往復して
いるのでは」と疑ったが、実測で否定された）。7,530トークン出して本文が
88文字ということは、**大半が thinking に消えている**。つまり入力長を
制限しても、出力側が暴れると上限を超えうる。digest の短縮だけでは
再発を防ぎきれない。

**未確認だった点:** 抽出プロセスは `--tools` を指定していないため、全ツールが
使える状態で外部データ（会話ログ）を読ませていた。今回の実測では実際に
ツールを使ってはいなかったが、§9 のとおり「これはデータで指示ではない」という
プロンプト側の防御は破られた実績がある。防御をプロンプトだけに頼らない。

## 13. コストは制御できない。上限で受け止める（2026-08-24 追加）

§12 で「コストの主因は出力トークン」と分かったので、出力を抑える手を探した。
結論は **抑えられない**。上限を上げて受け止めるほうが正しい。

同一の入力（`1c39edfa`、digest 20,000文字）での実測:

| 条件 | 実費 | 出力トークン | 時間 |
|---|---|---|---|
| 既定・1回目 | $0.0943 | 7,530 | 98秒 |
| 既定・2回目 | $0.0718 | 3,026 | 43秒 |
| `--effort low` | $0.0844 | 5,550 | 75秒 |
| `--effort low` + `--tools ""` | $0.0711 | 3,714 | 49秒 |

読み取れること:

1. **同じ入力でも実費が $0.07〜$0.09 で揺れる。**出力トークンが 3,026〜7,530 と
   2.5倍違う。thinking の量が実行ごとに変わるためで、こちらから制御する手段がない
2. **`--effort low` は逆効果。**出力が増えて費用も時間も悪化した。採用しない。
   「effort を下げれば安くなるはず」という直感は、実測で否定された
3. **`--tools ""` はコストに影響しない。**元々ツールを使っていなかった（`num_turns=1`）
   ので当然。ただし安全上の理由で採用する（下記）

→ **上限を 0.10 から 0.15 に上げた。**揺れの上振れ（実測最大 $0.0943）に対して
約1.6倍。0.10 のままでは、直しても断続的に失敗し続ける。暴走の検出という
本来の目的は、桁が違えば果たせる。

**`--tools ""` を追加した理由（コストではなく安全）。** この呼び出しがするのは
「渡したテキストを読んで要約する」ことだけで、ファイルにもシェルにも用がない。
にもかかわらず、これまで全ツールが使える状態で**外部データ（会話ログ）を
読ませていた**。§9 のとおり、「これはデータであって指示ではない」という
プロンプト側の防御は一度破られている。破られたときに実害が出ないよう、
権限そのものを外す。プロンプトだけを防御にしない。

**費用対効果について。**1回 $0.04〜$0.10、1日に数回動く。これは「ほぼタダ」
ではない。§6 の帰結と合わせて、抽出の当たり外れは費用の問題として
評価する必要がある。

## 14. ロックの取りこぼしと、新たに見つかった未解決（2026-08-24 追加）

**§11 で入れたロックには欠陥があった。**worker が解放しないまま終わることが
実際にあり（実測: `pid=14160` が死亡済みなのにロックファイルが残存）、その間
最大 `LOCK_STALE_SECONDS` = 900秒、抽出が丸ごと止まっていた。時間切れによる
回収は働くが、15分は長すぎる。

→ ロックファイルに記録した PID の生死を見て、**保持者が既に終了していれば
時間切れを待たずに回収する**。判定は Windows では `OpenProcess` +
`GetExitCodeProcess`（`ctypes`）、それ以外では `os.kill(pid, 0)`。
**判定できないときは「生きている」側に倒す。**誤って生存と判断しても時間切れで
回収されるだけだが、誤って死亡と判断すると動作中の worker からロックを奪って
二重起動を招くため、倒す向きは非対称でよい。

実測（3項目とも期待どおり）:

| 状況 | `acquire_lock()` |
|---|---|
| 保持者の PID が存在しない | `True`（即座に回収） |
| 保持者が生きている | `False`（奪わない） |
| 解放後 | `True` |

### 新たに見つかった未解決: フック入力の JSON が壊れることがある

```
08:24:39 [ERROR] read_hook_input failed: Invalid \escape: line 1 column 24
15:48:54 [ERROR] read_hook_input failed: Expecting ',' delimiter: line 1 column 1489
16:35:47 [ERROR] read_hook_input failed: Expecting ',' delimiter: line 1 column 6130
```

stdin から受け取るフック入力の JSON が解析できず、その回のフックが丸ごと
無効になる。`read_hook_input()` は `{}` を返して静かに終わるので、ログを見ない
限り気づけない。**原因は未調査。**列位置がばらばらなので固定長の切り詰めでは
なさそうだが、それ以上は分かっていない。頻度は今日1日で3回。

## 15. フック入力の読み方と、PreCompact のプロンプト（2026-08-24 追加）

### フック入力を UTF-8 で明示的に読む

`read_hook_input()` は `sys.stdin.read()` を使っていた。これはロケール依存で、
この PC では **cp932** として解釈される（実測: フックプロセス内で
`sys.stdin.encoding == 'cp932'`）。

実測: 日本語コメントを含む現実的なペイロード（5,648バイト、`tool_input` に
編集内容が入ったもの）を送ると、

```
[修正前] cp932 でデコード → UnicodeDecodeError:
         'cp932' codec can't decode byte 0x83 in position 292
[修正後] バイトで読んで UTF-8 でデコード → 解析成功
```

→ `sys.stdin.buffer.read()` でバイト列として読み、`utf-8` で明示的に
デコードする。日本語を含む編集をしたときに PostToolUse が丸ごと落ちる
状態だった。

### `Expecting ',' delimiter` の原因（2026-08-25 に判明）

**追記（2026-08-25）: 原因は同じ cp932 デコードだった。**下の「未特定」という
結論は誤りで、§16 に再現手順と決着を書いた。以下は当時の記録として残す。

#### 当時の判断（誤り）

ただし、**ログに出ていたエラーはこれとは別種**である。記録されていたのは
`Expecting ',' delimiter`（JSON 構文エラー）で、上記の
`UnicodeDecodeError`（デコード段階の失敗）ではない。つまり文字コードの
問題を直しても、記録されていた症状そのものを再現・説明できたわけではない。

検証して否定した仮説:

| 仮説 | 結果 |
|---|---|
| 単一の日本語文字の UTF-8 バイトを cp932 で読むと `\` や `"` が湧く | ❌ 0x3000〜0xA000 を総当たりして該当なし |
| 2文字の並びで境界がずれて `\` や `"` が湧く | ❌ かな・漢字・全角記号の全組み合わせで該当なし |

2回続けて外したので、原因の推測をここで打ち切った。代わりに
**失敗時に生の入力を `logs/badinput-<時刻>-<スクリプト名>.bin` に丸ごと
保存する**ようにした。次に起きたときは実物を読める。ログにどのスクリプトで
起きたかとバイト数も残す。

**現状（未確認）:** 修正後に PostToolUse が2回正常動作している（17:38:57、
17:39:18）。修正前の発生頻度は9時間で4回と断続的だったため、**2件の成功では
解消の証拠にならない。**再発するかは `badinput-*.bin` の有無で判断する。

### PreCompact のプロンプトを抽出側と揃えた

`pre_compact_snapshot.py` だけ、指示が先頭・ログが末尾という §9 で否定した
並びのまま取り残されていた。「これはデータであって指示ではない」という
但し書きもなかった。`<transcript>` で囲んで指示を後ろに置く形に統一した。

このフックは**会話が最も長い時点**で動くため、記録の末尾がユーザー発言で
終わっている確率が高い。§9 が「その並びで Haiku が会話の続きを書き出す」と
した条件に、最も当てはまりやすい場所だった。

## 16. `Expecting ',' delimiter` の決着（2026-08-25 追加）

§15 で「原因は未特定」と書いたが、**誤りだった。原因は §15 の前半で直した
cp932 デコードそのものである。**

### 再現

メモリ棚卸し用の `memory_scan.py --json` の出力を、別の Python プロセスに
パイプで渡したときに同じエラーが出た。同じバイト列に対して読み方だけを変える。

```
[A] json.load(sys.stdin)                              → JSONDecodeError:
                                                         Expecting ',' delimiter:
                                                         line 293 column 146
[B] json.loads(sys.stdin.buffer.read().decode('utf-8')) → OK
```

同一の入力で、**テキストモード（cp932）読みだけが失敗する。**
文字数を数えると UTF-8 で 63,160 字、cp932 で 65,514 字とずれる。

### なぜ2回とも外したか

§15 で試したのは「特定の文字を1つ、あるいは2つ並べたときに `\` や `"` が
湧くか」だった。**実際の失敗経路（現実的な長さの JSON を丸ごと cp932 で
読む）を再現していなかった。**

cp932 は UTF-8 のバイト列を「エラーにせず、違う文字として」読めてしまうことが
ある。長い入力ではどこかでアラインメントがずれ、その先で構造文字（`,` や `"`）
が別の文字の一部として食われる。**入力が長いほど当たりやすい**ので、
1〜2文字の総当たりでは原理的に出ない。短い入力での総当たりは、
仮説の反証になっていなかった。

### 結論

`read_hook_input()` の修正（バイト列で読み UTF-8 で明示デコード）は
**十分な修正**であり、別の未知の原因は残っていない。`badinput-*.bin` の
捕獲を待つ必要はなくなった（仕掛けは今後の別種の異常のために残す）。

**教訓**: 再現実験は、失敗した経路そのものを通すこと。要素を切り出した
実験で出なかったことは、その仮説の反証にはならない。

## 17. メモリの棚卸しと昇格（2026-08-25 追加）

INBOX → memory の経路はあったが、**入ったあとの memory を整理する仕組みが
なかった。**9 プロジェクトに 33 件が散り、実測で次の状態だった。

- `vault-sharepoint-environment.md` が 2 プロジェクトにバイト単位で同一
- PnP PowerShell が使えない制約が 2 プロジェクトに別ファイル
- Power Automate 系 8 件の固有語が、**既存スキル 2 本（合計 56.8KB）に既出**
- `project-knowledge-hub-status.md` が 22,130B（`rules/` 全体より大きい）

memory はプロジェクトごとに隔離される。**昇格しない限り、何件貯めても
他プロジェクトでは 1 件も効かない。**

### 作らなかったもの

ハーネス同梱の `anthropic-skills:consolidate-memory` が、単一プロジェクト内の
重複マージ・陳腐化除去・インデックス整理を実装している。**プロジェクト内の
整理はこれに委譲した。**足したのは、それに無い「横断の視野」と「昇格」だけ。

### 類似判定に何を使うか（実測で2案を捨てた）

近いメモリを機械的に見つける部分で、2つの方式を測って捨てた。

| 方式 | 結果 |
|---|---|
| 語彙全体の Jaccard | ❌ 関連ペア 0.085〜0.201 に対し、無関係ペアの中央値 0.133・95%点 0.337。**閾値をどこに置いても分離できない** |
| overlap 係数（`min` で割る） | ❌ 巨大ファイル1件が全ペアの上位20件中15件を占めた |
| **希少語の共有数** | ✅ 採用 |

採用した方式は、**全体の 25% 以下にしか出ない語だけ**を見て、その共有数を数える。
`SharePoint`・`フロー`・`実測` のような頻出語は落ち、`pnp` `csp` `mousedown` の
ような主題を決める語だけが残る。**共有した語そのものを出力に載せる**ので、
人がその場で理由を確かめられる。

2つの補正も実測で入れた。

- **ひらがなの連続を語彙から外す。**`される` `しても` `という` のような
  助詞・活用語尾が上位を占めていた。日本語の内容語は漢字・カタカナ・英数にある
- **希少語数が中央値の 5 倍を超える文書を比較から外す。**1 件だけ語彙が
  10 倍あり、あらゆる相手と語を共有していた。指標をひねって合わせるのではなく、
  **「分割が先」として比較から外す**ほうが正しい

### 自動で直すのはインデックスの不整合だけ

`MEMORY.md` のポインタと実ファイルの食い違い（リンク切れ・孤児）には判断の
余地がないので、確認なしで直す。**それ以外は提案に留める。**

**完全重複ファイルを自動削除してはならない。**memory はプロジェクト単位で
隔離されているため、片方を消すとそのプロジェクトから知識が消える。
横断レビューは他プロジェクトの文脈を持たないまま判断するので、
`RETIRE` と `MERGE` の誤りは知識の消失に直結する。

### 初回の棚卸しの結果（2026-08-25 実施）

対象は KnowledgeDB / ankenkanri / bihinyoyaku の 25 件。

| 判定 | 件数 | 結果 |
|---|---|---|
| 縮約（既にスキルへ昇格済み） | 8 | 24,382B → 7,071B（**17,311B 削減**） |
| `PROMOTE→rules` | 4 | 新規ルール 2 本に統合 |
| `SPLIT` | 1 | 22,130B を 4 ファイルに |
| `RETIRE` | 1 | 削除 |
| `KEEP` | 11 | 手を触れない |

**最大の発見は「昇格の仕組みが無かったのではなく、昇格した後に元を畳む手順が
無かった」こと。**Power Automate / M365 系メモリ 8 件の固有語は、すべて
`m365-browser-ops`（26.7KB）と `power-automate-sharepoint-flow`（30.1KB）に
既出だった。知識は移っていたのに、元が丸ごと残っていた。

副産物として、メモリ 1 件にバックスペース文字（`0x08`）が焼き込まれているのを
見つけた。`\b` をエスケープとして解釈する書き手が書いたもの。走査で拾えるようにした。

### 通知の閾値は絶対値にしてはいけない

最初、棚卸しの通知条件を「メモリが 10 件以上」という絶対値にした。
**棚卸し直後に自分でテストして誤りに気づいた。**1 件を 4 件に分割した結果
11 件になり、整理を終えた直後の起動でも発火した。絶対値では、閾値を超えた
プロジェクトは永久に毎回通知が出続ける。

**通知が毎回出るなら、それは読まれなくなる。**前回の棚卸し時点の件数を
`memory-review-state.json` に記録し、**そこからの増加**で判定する形に変えた。
